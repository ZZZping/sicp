5.4显式控制求值器

在5.1中，我们看到了如何将简单的Scheme程序转换为寄存器机器的描述。现在我们将对更复杂的程序执行这种转换，即4.1.1–4.1.4的元循环求值器，它展示了如何用过程eval和apply来描述Scheme解释器的行为。我们在本节中开发的显式控制求值器展示了求值过程中使用的基本过程调用和参数传递机制如何用寄存器和栈上的操作来描述。此外，显式控制求值器可以作为Scheme解释器的一种实现，用与传统计算机原生机器语言非常相似的语言编写。该求值器可以由5.2的寄存器机器模拟器执行。或者，它可以作为构建Scheme求值器的机器语言实现，甚至用于求值Scheme表达式的专用机器的起点。图5.16展示了这样一种硬件实现：一块充当Scheme求值器的硅芯片。芯片设计者从类似于本节所述求值器的寄存器机器的数据通路和控制器规范开始，并使用设计自动化程序来构建集成电路布局。304

寄存器和操作

在设计显式控制求值器时，我们必须指定寄存器机器中要使用的操作。我们用抽象语法描述了元循环求值器，使用了诸如quoted?和make-procedure这样的过程。在实现寄存器机器时，我们可以将这些过程展开为基本表结构内存操作的序列，并在我们的寄存器机器上实现这些操作。然而，这会使我们的求值器非常长，用细节掩盖了基本结构。为了澄清表述，我们将把4.1.2中给出的语法过程以及4.1.3和4.1.4节中给出的用于表示环境和其他运行时数据的过程作为寄存器机器的基本操作包含进来。为了完全指定一个可以用低级机器语言编程或在硬件中实现的求值器，我们将使用5.3中描述的表结构实现，将这些操作替换为更基本的操作。

我们的Scheme求值器寄存器机器包括一个栈和七个寄存器：exp、env、val、continue、proc、argl和unev。Exp用于保存要求值的表达式，env包含要在其中进行求值的环境。在一次求值结束时，val包含在指定环境中对该表达式求值所获得的值。continue寄存器用于实现递归，如5.1.4中所述。（求值器需要递归调用自身，因为求值一个表达式需要求值其子表达式。）寄存器proc、argl和unev用于求值组合式。

我们不会提供数据通路图来展示求值器的寄存器和操作如何连接，也不会给出机器操作的完整列表。这些隐含在求值器的控制器中，将详细呈现。

5.4.1显式控制求值器的核心

求值器中的核心元素是从eval-dispatch开始的一系列指令。这对应于4.1.1中描述的元循环求值器的eval过程。当控制器从eval-dispatch开始时，它在由env指定的环境中求值由exp指定的表达式。当求值完成时，控制器将转到存储在continue中的入口点，并且val寄存器将保存表达式的值。与元循环eval一样，eval-dispatch的结构是对要计算的表达式的语法类型进行情况分析。305

eval-dispatch
  (test (op self-evaluating?) (reg exp))
  (branch (label ev-self-eval))
  (test (op variable?) (reg exp))
  (branch (label ev-variable))
  (test (op quoted?) (reg exp))
  (branch (label ev-quoted))
  (test (op assignment?) (reg exp))
  (branch (label ev-assignment))
  (test (op definition?) (reg exp))
  (branch (label ev-definition))
  (test (op if?) (reg exp))
  (branch (label ev-if))
  (test (op lambda?) (reg exp))
  (branch (label ev-lambda))
  (test (op begin?) (reg exp))
  (branch (label ev-begin))
  (test (op application?) (reg exp))
  (branch (label ev-application))
  (goto (label unknown-expression-type))
求值简单表达式

数和字符串（它们是自求值的）、变量、引用和lambda表达式没有需要求值的子表达式。对于这些，求值器只需将正确的值放入val寄存器，并在由continue指定的入口点继续执行。简单表达式的求值由以下控制器代码执行：

ev-self-eval
  (assign val (reg exp))
  (goto (reg continue))
ev-variable
  (assign val
          (op lookup-variable-value)
          (reg exp)
          (reg env))
  (goto (reg continue))
ev-quoted
  (assign val
          (op text-of-quotation)
          (reg exp))
  (goto (reg continue))
ev-lambda
  (assign unev
          (op lambda-parameters)
          (reg exp))
  (assign exp 
          (op lambda-body)
          (reg exp))
  (assign val 
          (op make-procedure)
          (reg unev)
          (reg exp)
          (reg env))
  (goto (reg continue))

观察ev-lambda如何使用unev和exp寄存器来保存lambda表达式的参数和体，以便它们可以与env中的环境一起传递给make-procedure操作。

求值过程应用

过程应用由包含运算符和运算对象的组合式指定。运算符是一个子表达式，其值是一个过程，而运算对象是子表达式，其值是过程应被应用到的参数。元循环eval通过递归调用自身来求值组合式的每个元素，然后将结果传递给apply，后者执行实际的过程应用，从而处理应用。显式控制求值器做同样的事情；这些递归调用由goto指令实现，同时使用栈来保存将在递归调用返回后恢复的寄存器。在每次调用之前，我们将小心地确定哪些寄存器必须保存（因为它们的值稍后将被需要）。306

我们通过求值运算符以产生一个过程来开始应用求值，该过程稍后将应用于已求值的运算对象。为了求值运算符，我们将其移动到exp寄存器并转到eval-dispatch。env寄存器中的环境已经是求值运算符的正确环境。然而，我们保存env，因为稍后求值运算对象时需要它。我们还将运算对象提取到unev中并将此保存在栈上。我们设置continue，以便在运算符求值后，eval-dispatch将在ev-appl-did-operator处恢复。然而，首先我们保存continue的旧值，它告诉控制器在应用之后继续的位置。

ev-application
  (save continue)
  (save env)
  (assign unev (op operands) (reg exp))
  (save unev)
  (assign exp (op operator) (reg exp))
  (assign
   continue (label ev-appl-did-operator))
  (goto (label eval-dispatch))

从求值运算符子表达式返回后，我们继续求值组合式的运算对象，并将结果参数累积在一个表中，该表保存在argl中。首先我们恢复未求值的运算对象和环境。我们将argl初始化为空表。然后我们将通过求值运算符产生的过程赋值给proc寄存器。如果没有运算对象，我们直接转到apply-dispatch。否则我们将proc保存在栈上并开始参数求值循环：307

ev-appl-did-operator
  (restore unev)             ; the operands
  (restore env)
  (assign argl (op empty-arglist))
  (assign proc (reg val))    ; the operator
  (test (op no-operands?) (reg unev))
  (branch (label apply-dispatch))
  (save proc)

参数求值循环的每个周期从unev中的表求值一个运算对象，并将结果累积到argl中。为了求值一个运算对象，我们将其放入exp寄存器并转到eval-dispatch，在设置continue以便执行将在参数累积阶段恢复之后。但首先我们保存到目前为止累积的参数（保存在argl中）、环境（保存在env中）以及剩余要计算的运算对象（保存在unev中）。对最后一个运算对象的求值做了特殊处理，在ev-appl-last-arg处处理。

ev-appl-operand-loop
  (save argl)
  (assign exp
          (op first-operand)
          (reg unev))
  (test (op last-operand?) (reg unev))
  (branch (label ev-appl-last-arg))
  (save env)
  (save unev)
  (assign continue 
          (label ev-appl-accumulate-arg))
  (goto (label eval-dispatch))

当一个运算对象被求值后，该值被累积到argl中保存的表里。然后该运算对象从unev中的未求值运算对象表中移除，参数求值继续。

ev-appl-accumulate-arg
  (restore unev)
  (restore env)
  (restore argl)
  (assign argl 
          (op adjoin-arg)
          (reg val)
          (reg argl))
  (assign unev
          (op rest-operands)
          (reg unev))
  (goto (label ev-appl-operand-loop))

最后一个参数的求值处理方式不同。在转到eval-dispatch之前不需要保存环境或未求值运算对象表，因为在最后一个运算对象求值后它们将不再需要。因此，我们从求值返回到一个特殊入口点ev-appl-accum-last-arg，它恢复参数表，累积新参数，恢复保存的过程，并转去执行应用。308

ev-appl-last-arg
  (assign continue 
          (label ev-appl-accum-last-arg))
  (goto (label eval-dispatch))
ev-appl-accum-last-arg
  (restore argl)
  (assign argl 
          (op adjoin-arg)
          (reg val)
          (reg argl))
  (restore proc)
  (goto (label apply-dispatch))

参数求值循环的细节决定了解释器求值组合式运算对象的顺序（例如，从左到右或从右到左——参见习题3.8）。这个顺序不是由元循环求值器决定的，元循环求值器从其实现所基于的Scheme继承控制结构。309因为first-operand选择函数（在ev-appl-operand-loop中用于从unev中提取连续的运算对象）实现为car，而rest-operands选择函数实现为cdr，所以显式控制求值器将按从左到右的顺序求值组合式的运算对象。

过程应用

入口点 apply-dispatch 对应于元循环求值器的 apply 过程。当我们到达 apply-dispatch 时，proc 寄存器包含要应用的过程，argl 包含必须应用该过程的已求值参数的表。continue 的保存值（最初传递给 eval-dispatch 并在 ev-application 处保存），它指示在何处返回过程应用的结果，位于栈上。当应用完成时，控制器转移到由保存的 continue 指定的入口点，应用的结果在 val 中。与元循环 apply 一样，有两种情况需要考虑。要应用的过程要么是基本过程，要么是复合过程。

apply-dispatch
  (test (op primitive-procedure?) (reg proc))
  (branch (label primitive-apply))
  (test (op compound-procedure?) (reg proc))
  (branch (label compound-apply))
  (goto (label unknown-procedure-type))

我们假设每个基本过程的实现都从 argl 获取其参数，并将其结果放入 val。为了说明机器如何处理基本过程，我们必须提供一系列控制器指令来实现每个基本过程，并安排 primitive-apply 分派到由 proc 的内容所标识的基本过程的指令。由于我们感兴趣的是求值过程的结构而非基本过程的细节，我们将改为仅使用一个 apply-primitive-procedure 操作，将 proc 中的过程应用于 argl 中的参数。为了用 5.2 的模拟器模拟求值器，我们使用过程 apply-primitive-procedure，它调用底层的 Scheme 系统来执行应用，正如我们在 4.1.4 中对元循环求值器所做的那样。在计算基本过程应用的值之后，我们恢复 continue 并转到指定的入口点。

primitive-apply
  (assign val (op apply-primitive-procedure)
              (reg proc)
              (reg argl))
  (restore continue)
  (goto (reg continue))

要应用复合过程，我们就像元循环求值器那样进行。我们构造一个框架，将过程的形参绑定到实参上，使用这个框架来扩展过程所携带的环境，并在这个扩展环境中求值构成过程体的表达式序列。Ev-sequence，下面在 5.4.2 中描述，处理序列的求值。

compound-apply
  (assign unev 
          (op procedure-parameters)
          (reg proc))
  (assign env
          (op procedure-environment)
          (reg proc))
  (assign env
          (op extend-environment)
          (reg unev)
          (reg argl)
          (reg env))
  (assign unev
          (op procedure-body)
          (reg proc))
  (goto (label ev-sequence))

Compound-apply 是解释器中唯一给 env 寄存器赋新值的地方。正如在元循环求值器中一样，新环境由过程所携带的环境，连同参数表和要绑定的相应变量表一起构造。

5.4.2序列求值与尾递归

显式控制求值器中 ev-sequence 处的部分类似于元循环求值器的 eval-sequence 过程。它处理过程体或显式 begin 表达式中的表达式序列。

显式 begin 表达式的求值方式是将要求值的表达式序列放入 unev，将 continue 保存在栈上，并跳转到 ev-sequence。

ev-begin
  (assign unev
          (op begin-actions)
          (reg exp))
  (save continue)
  (goto (label ev-sequence))

过程体中的隐式序列通过从 compound-apply 跳转到 ev-sequence 来处理，此时 continue 已经在栈上，是在 ev-application 处保存的。

ev-sequence 和 ev-sequence-continue 处的入口形成一个循环，依次求值序列中的每个表达式。未求值表达式的表保存在 unev 中。在求值每个表达式之前，我们检查序列中是否还有要额外求值的表达式。如果有，我们保存剩余的未求值表达式（保存在 unev 中）以及必须求值这些表达式的环境（保存在 env 中），并调用 eval-dispatch 来求值该表达式。这两个保存的寄存器在从这次求值返回时，在 ev-sequence-continue 处恢复。

序列中的最后一个表达式在入口点 ev-sequence-last-exp 处以不同方式处理。由于在这个表达式之后没有更多表达式需要求值，我们不必在转到 eval-dispatch 之前保存 unev 或 env。整个序列的值是最后一个表达式的值，因此在求值最后一个表达式之后，除了在当前保存在栈上的入口点继续之外（该入口点由 ev-application 或 ev-begin 保存），没有其他事情要做。与其设置 continue 来安排 eval-dispatch 返回到这里，然后从栈上恢复 continue 并在该入口点继续，我们不如在转到 eval-dispatch 之前从栈上恢复 continue，这样 eval-dispatch 将在求值该表达式之后在该入口点继续。

ev-sequence
  (assign exp (op first-exp) (reg unev))
  (test (op last-exp?) (reg unev))
  (branch (label ev-sequence-last-exp))
  (save unev)
  (save env)
  (assign continue
          (label ev-sequence-continue))
  (goto (label eval-dispatch))
ev-sequence-continue
  (restore env)
  (restore unev)
  (assign unev
          (op rest-exps)
          (reg unev))
  (goto (label ev-sequence))
ev-sequence-last-exp
  (restore continue)
  (goto (label eval-dispatch))
尾递归

在 第 1 章中，我们说过，由诸如以下过程描述的计算过程

(define (sqrt-iter guess x)
  (if (good-enough? guess x)
      guess
      (sqrt-iter (improve guess x) x)))

是一个迭代计算过程。尽管该过程在语法上是递归的（用自身定义），但求值器在从一个 sqrt-iter 调用传递到下一个调用时，逻辑上并不需要保存信息。310 一个能够执行诸如 sqrt-iter 这样的过程，而随着过程继续调用自身不需要增加存储的求值器，称为 尾递归求值器。第 4 章中求值器的元循环实现没有指定求值器是否是尾递归的，因为该求值器从底层 Scheme 继承其保存状态的机制。然而，使用显式控制求值器，我们可以追踪求值过程，以查看过程调用何时导致栈上信息的净累积。

我们的求值器是尾递归的，因为为了求值序列的最后一个表达式，我们直接转移到 eval-dispatch 而不在栈上保存任何信息。因此，求值序列中的最后一个表达式——即使它是一个过程调用（如在 sqrt-iter 中，其中 if 表达式，即过程体中的最后一个表达式，归约为对 sqrt-iter 的调用）——不会导致任何信息在栈上累积。311

如果我们没有想到利用在这种情况下不需要保存信息这一事实，我们可能会通过以相同方式处理序列中的所有表达式来实现eval-sequence——保存寄存器、求值表达式、返回以恢复寄存器，并重复此过程直到所有表达式都被求值：312

ev-sequence
  (test (op no-more-exps?) (reg unev))
  (branch (label ev-sequence-end))
  (assign exp (op first-exp) (reg unev))
  (save unev)
  (save env)
  (assign continue
          (label ev-sequence-continue))
  (goto (label eval-dispatch))
ev-sequence-continue
  (restore env)
  (restore unev)
  (assign unev (op rest-exps) (reg unev))
  (goto (label ev-sequence))
ev-sequence-end
  (restore continue)
  (goto (reg continue))

这看起来可能只是对我们之前用于求值序列的代码的一个微小改动：唯一的区别在于，我们不仅对其他表达式，而且对序列中的最后一个表达式也执行保存-恢复循环。解释器对于任何表达式仍然会给出相同的值。但这一改动对于尾递归实现是致命的，因为我们现在必须在求值序列中的最后一个表达式之后返回，以便撤销（无用的）寄存器保存。这些额外的保存在嵌套的过程调用期间会累积。因此，诸如sqrt-iter这样的计算过程将需要与迭代次数成比例的空间，而不是需要常量空间。这种差异可能很显著。例如，使用尾递归，可以仅用过程调用机制来表达一个无限循环：

(define (count n)
  (newline)
  (display n)
  (count (+ n 1)))

如果没有尾递归，这样的过程最终会耗尽栈空间，而表达真正的迭代将需要某种过程调用之外的控制机制。

5.4.3条件式、赋值和定义

与元循环求值器一样，特殊形式通过选择性地求值表达式的片段来处理。对于if表达式，我们必须求值谓词，并根据谓词的值决定是求值结果表达式还是求值替代表达式。

在求值谓词之前，我们保存if表达式本身，以便稍后能提取结果表达式或替代表达式。我们还保存环境，稍后求值结果表达式或替代表达式时需要它，并且我们保存continue，稍后返回等待if值的表达式的求值过程时需要它。

ev-if
  (save exp)   ; save expression for later
  (save env)
  (save continue)
  (assign continue (label ev-if-decide))
  (assign exp (op if-predicate) (reg exp))
  ; evaluate the predicate:
  (goto (label eval-dispatch))

当我们从求值谓词返回时，我们测试它是真还是假，并根据结果，在转到eval-dispatch之前将结果表达式或替代表达式放入exp。注意，这里恢复env和continue使得eval-dispatch具有正确的环境，并在正确的位置继续以接收if表达式的值。

ev-if-decide
  (restore continue)
  (restore env)
  (restore exp)
  (test (op true?) (reg val))
  (branch (label ev-if-consequent))
ev-if-alternative
  (assign exp (op if-alternative) (reg exp))
  (goto (label eval-dispatch))
ev-if-consequent
  (assign exp (op if-consequent) (reg exp))
  (goto (label eval-dispatch))
赋值和定义

赋值由ev-assignment处理，它从eval-dispatch到达，赋值表达式在exp中。ev-assignment处的代码首先求值表达式的值部分，然后将新值安装到环境中。假定Set-variable-value!可作为机器操作使用。

ev-assignment
  (assign unev 
          (op assignment-variable)
          (reg exp))
  (save unev)   ; save variable for later
  (assign exp
          (op assignment-value)
          (reg exp))
  (save env)
  (save continue)
  (assign continue
          (label ev-assignment-1))
  ; evaluate the assignment value:
  (goto (label eval-dispatch))  
ev-assignment-1
  (restore continue)
  (restore env)
  (restore unev)
  (perform (op set-variable-value!)
           (reg unev)
           (reg val)
           (reg env))
  (assign val
          (const ok))
  (goto (reg continue))

定义以类似方式处理：

ev-definition
  (assign unev 
          (op definition-variable)
          (reg exp))
  (save unev)   ; save variable for later
  (assign exp 
          (op definition-value)
          (reg exp))
  (save env)
  (save continue)
  (assign continue (label ev-definition-1))
  ; evaluate the definition value:
  (goto (label eval-dispatch))  
ev-definition-1
  (restore continue)
  (restore env)
  (restore unev)
  (perform (op define-variable!)
           (reg unev)
           (reg val)
           (reg env))
  (assign val (const ok))
  (goto (reg continue))

5.4.4运行求值器

随着显式控制求值器的实现，我们到达了一个始于第1章的发展的终点，在其中我们探索了越来越精确的求值过程模型。我们从相对非正式的代换模型开始，然后在第3章中将其扩展到环境模型，这使我们能够处理状态和变化。在第4章的元循环求值器中，我们使用Scheme本身作为一种语言，来更明确地表达在求值表达式期间构造的环境结构。现在，借助寄存器机器，我们仔细考察了求值器的存储管理、参数传递和控制机制。在每一个新的描述层次上，我们都不得不提出在前一个不那么精确的求值处理中不明显的问题并解决歧义。为了理解显式控制求值器的行为，我们可以模拟它并监视其性能。

我们将在求值器机器中安装一个驱动循环。它扮演4.1.4中driver-loop过程的角色。求值器将反复打印提示符、读取表达式、通过转到eval-dispatch来求值表达式，并打印结果。以下指令构成显式控制求值器的控制器序列的开头：314

read-eval-print-loop
  (perform (op initialize-stack))
  (perform (op prompt-for-input)
           (const ";;; EC-Eval input:"))
  (assign exp (op read))
  (assign env (op get-global-environment))
  (assign continue (label print-result))
  (goto (label eval-dispatch))
print-result
  (perform (op announce-output)
           (const ";;; EC-Eval value:"))
  (perform (op user-print) (reg val))
  (goto (label read-eval-print-loop))

当我们在过程中遇到错误（例如apply-dispatch处指示的“未知过程类型错误”）时，我们打印错误消息并返回驱动循环。315

unknown-expression-type
  (assign 
   val
   (const unknown-expression-type-error))
  (goto (label signal-error))
unknown-procedure-type
  ; clean up stack (from apply-dispatch):
  (restore continue)    
  (assign 
   val
   (const unknown-procedure-type-error))
  (goto (label signal-error))
signal-error
  (perform (op user-print) (reg val))
  (goto (label read-eval-print-loop))

为了模拟的目的，我们在每次通过驱动循环时初始化栈，因为在错误（例如未定义变量）中断求值之后，栈可能不是空的。316

如果我们组合5.4.1–5.4.4中呈现的所有代码片段，我们就可以创建一个求值器机器模型，可以使用5.2的寄存器机器模拟器来运行它。

(define eceval
  (make-machine
   '(exp env val proc argl continue unev)
   eceval-operations
   '(read-eval-print-loop
     ⟨entire machine controller 
      as given above⟩)))

我们必须定义Scheme过程来模拟求值器用作基本操作的那些操作。这些过程与我们在4.1中用于元循环求值器的过程相同，再加上在5.4中脚注里定义的少数几个额外过程。

(define eceval-operations
  (list (list 'self-evaluating? 
              self-evaluating)
        ⟨complete list of operations 
         for eceval machine⟩))

最后，我们可以初始化全局环境并运行求值器：

(define the-global-environment
  (setup-environment))

(start eceval)

;;; EC-Eval input:
(define (append x y)
  (if (null? x)
      y
      (cons (car x) (append (cdr x) y))))

;;; EC-Eval value:
ok

;;; EC-Eval input:
(append '(a b c) '(d e f))

;;; EC-Eval value:
(a b c d e f)

当然，以这种方式求值表达式会比我们直接将它们输入 Scheme 中花费长得多的时间，因为涉及了多层次的模拟。我们的表达式由显式控制求值器机器求值，该机器由一个 Scheme 程序模拟，而这个 Scheme 程序本身又由 Scheme 解释器求值。

监控求值器的性能

模拟可以成为指导求值器实现的强大工具。模拟不仅便于探索寄存器机器设计的各种变体，还便于监控被模拟求值器的性能。例如，性能的一个重要因素是求值器使用栈的效率。我们可以通过用收集栈使用统计信息的模拟器版本（5.2.4）定义求值器寄存器机器，并在求值器的 print-result 入口点添加一条指令来打印统计信息，从而观察求值各种表达式所需的栈操作次数：

print-result
  ; added instruction:
  (perform (op print-stack-statistics))
  (perform (op announce-output)
           (const ";;; EC-Eval value:"))
  … ; same as before

现在与求值器的交互看起来像这样：

;;; EC-Eval input:
(define (factorial n)
  (if (= n 1) 1 (* (factorial (- n 1)) n)))
(total-pushes = 3, maximum-depth = 3)

;;; EC-Eval value:
ok

;;; EC-Eval input:
(factorial 5)
(total-pushes = 144, maximum-depth = 28)

;;; EC-Eval value:
120

注意，求值器的驱动循环在每次交互开始时重新初始化栈，因此打印的统计信息将仅涉及用于求值前一个表达式的栈操作。

习题 5.26： 使用被监控的栈来探索求值器的尾递归性质（5.4.2）。启动求值器并定义来自 1.2.1 的迭代 factorial 过程：

(define (factorial n)
  (define (iter product counter)
    (if (> counter n)
        product
        (iter (* counter product)
              (+ counter 1))))
  (iter 1 1))

习题 5.29： 监控树形递归斐波那契 计算中的栈操作：

(define (fib n)

      n
      (+ (fib (- n 1)) (fib (- n 2)))))
  1. 给出一个以 n 表示的公式，用于计算对 n ≥ 2 计算 Fib ( n ) 所需的最大栈深度。提示：在 1.2.2 中我们论证了此计算过程使用的空间随 n 线性增长。

习题 5.30： 我们的求值器目前只捕获并发出两种错误——未知表达式类型和未知过程类型。其他错误会使我们退出求值器的读取-求值-打印循环。当我们使用寄存器机器模拟器运行求值器时，这些错误由底层的 Scheme 系统捕获。这类似于用户程序出错时计算机崩溃。317 使真正的错误系统工作是一个大项目，但理解这里涉及的内容是非常值得的。

  1. 求值过程中发生的错误，例如试图访问未绑定的变量，可以通过更改查找操作使其返回一个特殊的条件码来捕获，该条件码不可能是任何用户变量的可能值。求值器可以测试此条件码，然后执行必要的操作以转到 signal-error。找出求值器中所有需要进行此类更改的地方并修复它们。这是大量的工作。
  2. 更糟糕的是处理由应用基本过程所引发的错误，例如试图除以零或试图提取符号的car。在专业编写的高质量系统中，每次基本过程应用都作为基本过程的一部分进行安全检查。例如，每次调用car都可以首先检查参数是否为序对。如果参数不是序对，应用将向求值器返回一个特殊的条件码，求值器随后报告失败。我们可以在寄存器机器模拟器中安排这一点，让每个基本过程检查适用性，并在失败时返回适当的特殊条件码。然后求值器中的primitive-apply代码可以检查条件码，并在必要时转到signal-error。构建这个结构并使其工作。这是一个大项目。
